# 운영 런북 — 현대엔지니어링 가치체계 내재화 워크숍 시스템

## 1. 운영 전날

| # | 할 일 | 방법 |
|---|---|---|
| 1 | 내일 차수의 일정·장소·강의실·FT·예상 인원 확인 | 콘솔 → 차수 관리 → 편집 (번호·날짜를 바꿔도 QR은 그대로) |
| 2 | 자동 리허설 1회 | `npm run rehearsal -- https://배포주소` → **27개 통과** 확인 |
| 3 | QR 시트 인쇄 | 콘솔 → 오늘의 운영 → 날짜를 내일로 → **QR 시트 인쇄** (A4 세로, 여백 없음/최소, 배경 그래픽 켜기). 방마다 테두리 색이 다름: A 주황 · B 초록 · C 파랑 |
| 4 | 현황판 링크 전달 | 콘솔 → 현황판 카드 → **뷰어 공유 링크 복사** (고객사 담당자용. 통계만 보이고 원문은 안 보임) |
| 5 | 실기기 점검 (아래 §4) | 아이폰 1대 + 안드로이드 1대로 내일 차수 QR을 찍어 허브가 열리는지 |

## 2. 운영 당일

1. **시작 전**: 콘솔 → 오늘의 운영. 오늘 차수 카드가 방 수만큼 보이는지 확인 → 각 카드 **진행 시작**.
2. **입장 안내**: 방에 붙인 QR 또는 오픈카톡에 **카톡 공지문**(카드의 버튼으로 복사) 1회 게시. 링크는 허브 1개뿐.
3. **모듈마다 토글**: 해당 활동의 스위치를 켠다 → 참여자 화면에 최대 17초 안에 활동명이 나타남.
   - 권장 순서: 2 시험공부(기본 열림) → 3 팀 정체성 → 4 조별 인재상 → 5 개인다짐 → 6 Pulse Check
   - **Pulse는 팀장 스피치 직전에** 연다(데이터가 깨끗함).
   - 제출 안내는 "지금부터 1~2분 동안 제출해 주세요"처럼 **시간을 두고** 한다. 전원이 같은 1초에 누르게 하는 카운트다운은 피한다(§5 용량 참고).
4. **종료**: 실참석 인원 입력 → **차수 종료**. 미입력 시 현황판 누적 인원이 예상치로 잠정 집계되고 콘솔에 경고가 뜬다.
5. **백업**: 사무실 PC에서 `npm run backup` (1분). `backups/날짜_시각/`에 JSON + 엑셀 1권. 이 폴더는 원문이 들어 있으므로 외부 공유 금지.

## 3. 현장 장애 대응

| 증상 | 원인 · 조치 |
|---|---|
| 참여자 화면에 "연결되면 자동 전송" | 그 기기의 네트워크 문제. 입력은 기기에 저장돼 있고 연결되면 자동 전송. 그대로 두면 됨 |
| "아직 저장되지 않았어요 · 다시 시도" | 자동 재시도 3회 실패. **다시 시도** 버튼. 입력 내용은 남아 있음 |
| "지금은 이 활동이 열려 있지 않아요" | 토글이 꺼져 있음 → 콘솔에서 켠 뒤 참여자가 **다시 시도** |
| 허브에 활동이 안 나타남 | 토글 확인 → 참여자에게 화면을 한 번 내렸다 올리거나 새로고침 안내(최대 17초 지연) |
| 다른 방 QR로 제출함 | 콘솔 → 수집 데이터 → 해당 행 **차수 재지정** |
| 장난·오입력 | 수집 데이터 → **숨김** (현황판·집계에서 즉시 제외, 언제든 복원) |
| 명부에 없는 팀으로 제출됨 | 팀 명부 상단 노란 큐 → **명부에 추가**(신설 팀) 또는 **기존 팀에 병합**(오타·약칭) |
| 학습자료(아티팩트)가 안 열림 | 차수 관리 → 편집 → **학습자료 URL**에 대체 주소 입력. 인쇄된 QR은 그대로 유효 |
| 현황판 링크가 유출됨 | 콘솔 → 현황판 카드 → **토큰 재발급**. 기존 링크·QR 즉시 만료, 새 링크 재전달 |
| "이미 제출된 정체성이 있습니다" | 같은 팀의 다른 사람이 먼저 제출함. 팀 내 합의 후 **수정하기**(이전 본은 이력으로 보존) |
| 사이트 전체가 안 열림 | Vercel·Supabase 상태 페이지 확인. 참여자 입력은 각자 기기에 남아 있으므로 복구 후 재전송 가능. 최악의 경우 종이 제출 후 사후 입력 |

## 4. 실기기 점검표 (자동화 불가 — 사람이 해야 함)

iOS Safari는 필수, 그 외는 가능한 범위에서.

- [ ] **아이폰 카메라로 QR** → Safari에서 허브가 열린다. 상단 네이비 영역·번호 카드가 깨지지 않는다
- [ ] **카카오톡 링크**로 열기(인앱 브라우저) → 허브가 열리고 시험공부 자료가 열렸다가 뒤로 돌아올 수 있다
- [ ] 입력창을 눌러도 **화면이 확대되지 않는다**(글자 16px)
- [ ] 팀 이름 2글자 입력 → 목록이 뜨고, 선택하면 다음 폼에 자동으로 떠 있다
- [ ] 형용사·명사 칸을 누르면 Pool 칩 전체가 가나다순으로 뜬다. 한글 입력 후 **완료(엔터)** 시 마지막 글자가 중복되지 않는다
- [ ] 하단 저장 버튼이 **홈 인디케이터에 가리지 않는다**
- [ ] 작성 중 **비행기 모드 ON → 저장** → "연결되면 자동 전송" 안내 → **비행기 모드 OFF** → 자동으로 완료 화면 (DoD 4)
- [ ] 작성 중 탭을 닫았다 다시 열어도 입력이 남아 있다
- [ ] 저장 버튼을 빠르게 여러 번 눌러도 콘솔에 1건만 보인다
- [ ] 안드로이드 Chrome / 삼성 인터넷에서 위 항목 1·4·5·7

> 주의: **QR(Safari)로 들어온 사람과 카카오톡 링크(인앱 브라우저)로 들어온 사람은 서로 다른 '기기'로 취급**된다(저장소가 분리됨).
> 한 사람이 두 경로를 오가면 기억된 팀·작성 중 초안이 이어지지 않고, 개인다짐이 2건 생길 수 있다. 입장 경로는 하나로 안내한다.

## 5. 용량과 한계 (M5 부하 테스트 결과)

측정 환경: 이 PC의 프로덕션 빌드 1개 프로세스 + 실제 Supabase(도쿄). 가상 사용자 150명이 각자 허브 → 폼 → **제출 4회**(다짐 2 + Pulse 2, 재전송 포함).
실제 현장(1인 1제출)보다 약 4배 가혹한 조건이다.

| 시나리오 | 에러 | 유실·중복 | 제출 p95 | 판정 |
|---|---|---|---|---|
| 150명이 10초에 걸쳐 제출 시작 | 0% | 0 | **1.06초** | 통과 (< 2초) |
| 150명이 3초 안에 집중 | 0% | 0 | 4.9초 | 지연만 발생 |
| 150명이 같은 순간에 (최악) | 0% | 0 | 9.3초 | 지연만 발생 |

- 병목은 Supabase 인스턴스의 처리량(**초당 약 50건**, 1건당 78ms)이다. 어떤 경우에도 데이터는 유실·중복되지 않았고, 참여자 화면은 자동 재시도·초안 보존으로 방어한다.
- 150명 대형 차수에서 여유를 더 두려면 행사 기간에만 Supabase **Compute를 Small 이상으로** 올리는 것이 가장 효과적이다(대시보드 → Project Settings → Compute and Disk).
- 허브·폼 페이지는 2초 캐시로 Supabase 호출을 합친다(150명 동시 입장 시 허브 p50 6.7초 → 0.9초). 제출 시 잠금 검증은 매번 DB가 한다.
- Vercel 함수 리전은 Supabase와 같은 **도쿄(hnd1)** 로 고정했다(`vercel.json`). 기본값(미국 동부)이면 모든 제출이 태평양을 왕복한다.
- 배포 서버 대상 재측정: `npm run loadtest -- https://배포주소 150 10`

## 7. 명령어 모음

```bash
npm run rehearsal -- https://배포주소     # 운영 전날 자동 리허설 (임시 차수 생성 → 27개 점검 → 자동 삭제)
npm run loadtest  -- https://배포주소 150 10   # 부하 테스트 (사용자 수, 출발 분산 초)
npm run backup                            # 전체 데이터 로컬 백업 (JSON + 엑셀)
npm run admin:create                      # 운영자 추가·비밀번호 변경 (.env.local의 ADMIN_EMAIL/PASSWORD)
npm test                                  # 조사 처리 + DB 규칙 테스트
npm run dev:mock                          # 키 없이 로컬 데모 (/s/demo01, /dashboard?k=demo)
```
